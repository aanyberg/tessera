## 3. Structural lessons
1. **Performance had no bar until a critic invented one.** The #4 brief had no perf criterion; the bar appeared after R1 ("ASCII within 1.5x, CJK and Latin within 3x"), widened after R2 ("all common text"), and a fourth category (braille) surfaced in verification. Four iterations on an allow-list fast path (`is_simple` ranges), about 3 h of the critical path. The same hot function (`State::print`) was in #6's scope, which added a further 1.4-1.7x (R2) and a third round.
2. **Sibling tasks on one hot function.** #4 and #6 both changed `print`/REP behaviour. The planner's file partition worked (no merge conflict), but the semantic interaction (REP after clusters and early returns) cost a major in #6 R1, a cross-task rule from the #4 critic, and a perf regression from that rule. #6 critiqued once on the pre-#4 base (usefully, via `git merge-tree`) and twice more after.
3. **Dependent task idle.** #6 sat 141 min waiting for #4. The "integrate #4 first" plan assumed #4 would be fastest; it was slowest.
4. **Tolerance-based oracles and unbounded event paths.** Both verify-cycle failures were "the test or design passes by construction": a golden budget larger than any single attribute, and a callback bridge that coalesced output but not bells. Neither critic checklist asks for a mutation test of a tolerance or a flood test of an event path.
5. **Lead decisions the implementer skipped.** #32 R1's only major was a one-line fix the lead had already put in scope. A full critic round (34k tokens, 7 min) was then spent confirming it.
6. **Spec-heavy briefs contained wrong facts.** #6's Done-when named the wrong vttest menu and the "do not touch the grid" rule conflicted with five xterm mismatches; the lead appended 8-10 decisions to the #6 and #4 briefs. The spec-researcher fixed this, after hitting its turn limit.
7. **Post-ship edits are unreviewed.** The lead routinely sends nit, doc and test fixes after `ship` and after verification, without a new critic. For doc and test changes that is fine (saved at least one round on #26). For #4, the post-verify commit added three `is_simple` ranges and a width clamp (hot-path code) and went straight to integration with only the implementer's own tests.
8. **Stale-base handling worked.** Every branch merged main before critique or verification; no verifier reported a stale-base finding. ADR numbers and workspace deps were pre-assigned and had no collisions (0008, 0010, 0011, 0012; 0009 left unused).
9. **Friction (per lead summary, not verified in transcripts I read):** rebase-merge was disabled in repo settings, the user's `!` shell commands did not execute, and no shared task-list tool existed so the lead tracked tasks by message. In transcripts I confirmed the last point (lead: "No shared task-list tool is available in this session") and that teammates were told to report with SendMessage while the harness requires SubagentHandback (#4's teammate received "[handback-send-enforce] Your report has not been delivered" and sent the report twice).

## 4. Proposals (each with its evidence)
1. **spec-researcher: `maxTurns` 40 to 80, and add to the prompt "write the fixture file with the header and the first rows within your first 15 turns, then append; return the summary even if incomplete".** Evidence: both runs hit 40 with zero output (#6 at about 8 min, #4 at about 19 min), each needed a lead intervention and resume. Keep sonnet/high; the output was the highest-value artefact of the wave. The agent file already says "always finish by returning a summary"; that instruction did not survive the limit, so the limit and write-early rule are the fix.
2. **Performance bar in briefs for hot-path tasks (milestone-lead prompt and brief template).** Any task that changes a per-character, per-line or per-frame path must carry a bar with a named corpus (at minimum: ASCII, Latin/Vietnamese, CJK, box drawing, Hebrew, Arabic, punctuation, braille, emoji, SGR-heavy line, combining-heavy text reported) measured against main, interleaved, best of N. Evidence: #4 R1/R2 majors, braille at verify, #6 R2. Also add a "ratio table in the report" requirement to `rust-implementer` for such tasks, so the critic reviews numbers instead of discovering them.
3. **rust-critic prompt: for hot-path diffs, (a) benchmark against main on the brief's corpus, (b) differential-fuzz any fast path against the unoptimised reference, (c) when the brief names a sibling task that touches the same function, run `git merge-tree` on it and test the result.** Evidence: all three techniques produced the #4/#6 majors and nothing else did. This codifies what the critics did ad hoc, so it is a wording change, not extra effort. Keep opus/high; wall time 29 min on #4 was the benchmark build.
4. **Critic and adversarial prompts: two checklist lines.** (i) "A tolerance-based test (image diff, timing, count) must be shown to fail under a mutation of each behaviour it claims to cover"; (ii) "Every host callback or event emitted per input byte must be bounded: send a flood and watch memory and quit latency". Put (ii) in `swift-critic` and `rust-critic`, (i) in both critics. Evidence: #20 golden tolerance and #32 bell flood were each missed by two critic rounds and caught only by `adversarial-tester`.
5. **Implementer prompts (rust and swift): "Before reporting, tick every item in the brief's 'Lead decisions' section and list each in your report."** Evidence: #32 R1 major was an unapplied lead-approved fix; cost a 34k-token critic round.
6. **Runbook: post-ship change classification.** After `ship` or a verified pass, doc-only and test-only fixes go straight to the teammate and the lead checks the diff (no fresh critic); this is the existing practice and should be written down. Any change to non-test code in a hot path or a fast path after `ship` or after verification needs either a short fresh critic or a re-run of the adversarial differential on the changed region. Evidence: #26 skipped round 3 and passed (7 minors, none major); #32 R2 spent 34k tokens confirming a one-line fix; #4's post-verify `is_simple` additions were integrated unreviewed.
7. **Runbook: when a lead-decision-only fix remains, do not spend a round.** If a critic's only major is a doc line or a lead-approved item, the lead verifies the diff itself instead of a new critic (saves roughly 35k tokens and 7 min per case; one case this wave).
8. **Runbook: dependency scheduling.** Where two tasks change the same function, the planner marks one as upstream and the downstream task's critique waits for the upstream merge (or is limited to a merge-tree check). Integration order is "first verified first merged", not a fixed plan. Evidence: #6 idle 141 min and a planned order that was reversed in practice. Alternative to consider: do not put sibling `print` tasks in one wave.
9. **Runbook pre-flight checklist for the lead before step 1:** `gh api repos/<owner>/<repo> --jq '.allow_rebase_merge'` must print `true` (the PR gate section already requires it); also confirm the task-tracking mechanism. If rebase-merge is disabled, stop and ask the user before starting the wave rather than at merge time. Evidence: friction item per lead summary. Also document a fallback when `!` shell commands do not execute (give the user the exact `gh` command to run in a separate terminal, or use `gh api` from the lead).
10. **Runbook step 2 (task list):** state that when no task-list tool exists, the lead keeps a status table in its messages and addresses teammates by name (`impl-<n>`). Teammate spawn template: "report with SubagentHandback only; do not also SendMessage". Evidence: lead's own note, and the doubled report with the enforcement reminder in #4's transcript.
11. **No change to adversarial-tester (opus/xhigh).** It produced both verify failures (2 reproduced majors) plus the bulk of the minor defects (about 20) at 30% of tokens. The only low-yield run (#6) is n=1. Revisit if `high` is tried on grid/term-only tasks that already had critic differential fuzzing.
12. **quality-gate (haiku/low): keep.** 0 failures, 1.5% of tokens. Add to its prompt the brief's "accepted extras" list explicitly so that scope notes on listed files (#4 `lib.rs`, #20 `gpu.rs`) are not raised as flags. Minor.
13. **revision-implementer: leave defined, but update the runbook to say teammates normally apply findings themselves.** Evidence: 0 uses, 5/5 teammates revised in place with warm context.
14. **flow-analyst: `maxTurns` 40 to 80** (this analysis hit 40 before writing), and have the lead hand it a pre-extracted per-agent stats table (n, tokens, tools, span, verdicts). Evidence: this run was cut off and wrote the retro from partial reads; GitHub issue comments and the PR page were not read.
15. **milestone-lead (fable/medium): for spec-heavy issues, run the spec-researcher before finalising Done-when**, or mark the Done-when as provisional. Evidence: wrong vttest menu in #6, seven xterm mismatches contradicting "do not touch grid". The planner did well on collision avoidance (zero file or ADR collisions), so no model change.
