## What each gate actually caught
- Critique: 6/8 first-round "revise"; 10 major + 1 blocker (wgpu limits, portable-pty Drop ordering, unbounded OSC, polling instead of notify, unopenable config on parse error, kitty/xterm encoding divergences). Converged to ship in ≤3 rounds; rounds 4–5 never used.
- Acceptance verifier: never failed a task, yet reported 2 majors as pass=true (#18 error-scope threading, #33 single-watcher delivery). Pass criterion too loose; overlaps the critic.
- Quality gate: 1 failure, both findings were *integration* problems (duplicate ADR 0005 number, stale base vs advanced main). Otherwise mechanical and redundant with the critic's own check run.
- Adversarial: 6 failures / 7 majors, all real (git-cliff tag selection, wgpu `std` feature + thread-global error scopes, non-UTF-8 config, symlink loss in kqueue watcher, write_atomic temp-name race, Shift+keypad encoding). Highest value per token; also the longest single agent (22 min).
- Merge: cheap; only conflicts were Cargo.lock.

## Structural lessons
1. Parallel tasks need a lead that pre-assigns shared scarce resources (ADR numbers, new workspace deps, shared module names) — #33 and #37 both took ADR 0005.
2. Branches must merge current main before verification, otherwise verifiers report stale-base issues as findings.
3. Acceptance + quality lenses should be folded: one cheap mechanical gate (script-driven, low effort) and the critic owns "Done when". Keep adversarial as a separate, high-effort role.
4. Spec-heavy issues (#11 keyboard protocol: 311k tokens implement, 3 critique rounds, 2 verify cycles) benefit from a spec-research step that produces the test table before implementation.
5. Fix agents are the second-largest cost because each one re-reads the whole branch; give them the critic's findings plus the implementer's summary to shorten orientation.
6. Majors found by any verifier must fail the gate (acceptance passed with majors).
