# ADR 0001: Rust core with a native Swift shell

**Status:** accepted · 2026-10-27

## Context

We want iTerm2's native feel with a modern, fast, extensible core. Options
considered: (a) pure Rust UI with winit + wgpu and a custom toolkit, (b) pure
Rust UI with Zed's GPUI (Apache-2.0, published on crates.io, pre-1.0),
(c) native AppKit/SwiftUI shell over a Rust core, (d) Tauri/web UI.

## Decision

(c). Rust owns everything including the GPU-rendered terminal surface. Swift
owns windows, tabs, menus, Preferences, dialogs and system integration. The
frontend boundary is a C ABI generated by cbindgen, so another frontend can
be added under `apps/` without touching `crates/`.

## Consequences

- Native behaviour for free: IME, accessibility, Services, secure input,
  fullscreen, Stage Manager, Touch ID, Shortcuts.
- Two languages and two toolchains; the FFI surface must stay small and
  stable. Mitigation: the renderer is Rust, so the boundary carries events
  and commands, not pixels.
- Portability is "write a thin shell", not "recompile". GPUI remains an
  option for that shell later.
- Rejected (a)/(b): rebuilding preferences UI, accessibility and IME polish
  is the long pole, and GPUI's churn would couple our releases to Zed's.
  Rejected (d): input latency and font rendering are unacceptable for a
  terminal.
